# 헬창키우기 (가칭) — 제품 기획서 (V1)

> 이 문서는 프로젝트 소유자가 확정한 기획을 정리한 것이다. 코드/기능을 바꾸기 전에 먼저 이 문서를 갱신하고, 문서를 기준으로 구현한다.

## 0. 핵심 제품 정의 — 운동 기록 앱이 아니라 실시간 운동 연동 게임

**헬창키우기는 "운동한 내용을 나중에 직접 입력하는 운동 기록 앱"이 아니다.**

제품 핵심:

> **"운동 시작 버튼을 누르는 순간 현실 운동과 앱의 운동 세션이 동시에 시작되는 실시간 운동 연동 게임"**

기본 루프:

```
앱 실행
→ 홈에서 내 캐릭터 확인
→ [운동 시작]
→ 실시간 운동 세션 시작
→ 실제 운동
→ 운동 종류/상태 필요시 선택
→ 스탠리 반응
→ [운동 종료]
→ 운동 세션 자동 저장
→ 히스토리 생성
→ streak 갱신
→ 이후 실제 몸 변화 시 사진 업데이트
```

운동 기록(`WorkoutRecord`)은 플레이 자체가 아니라 **실시간 운동 세션(`WorkoutSession`)의 결과물**이다. 세션 도메인 상세는 [[architecture]]의 WorkoutSession lifecycle 참고.

절대 원칙: 운동 시간이 증가한다고 사용자의 몸 캐릭터가 자동으로 근육질로 변하지 않는다. EXP, 레벨, 전투력, RPG 성장, 자동 근육 진화 같은 가상 성장 시스템은 만들지 않는다 (2장 "가장 중요한 성장 원칙"과 동일 원칙). 실시간으로 반영되는 것은 운동 중 상태 / 실제 운동 시간 / 현재 운동 종류 / 현재 세션 / Stanley 반응 / streak / 운동 종료 결과뿐이다. 사용자의 실제 몸 외형 변화는 항상 새 사진 또는 사용자의 신체 데이터 업데이트를 근거로 한다.

## 0-A. WEIGHT CORE — V1 운동 CORE 최종 확정

**헬창키우기는 웨이트 중심 실시간 운동 게임이다. 사용자는 운동 후 기록하는 것이 아니라, 운동 시작 버튼을 누르고 실제 운동하면서 앱을 플레이한다. 기록은 플레이 결과로 자동 생성된다.**

**루틴은 선택 사항이다. 계획형/즉흥형/추천형 사용자를 모두 지원한다.**

**러닝/걷기/사이클은 보조 운동이며 웨이트와 동급의 제품 중심축이 아니다.**

이 세 문장은 V1의 운동 CORE 구조를 잠그는 기준이다. 이후 게임성/아트/AI/수익화/출시 품질은 이 구조 위에 추가하며, 명시적인 요청 없이 운동 CORE 구조 자체를 다시 설계하지 않는다. 상세 도메인(ExerciseDefinition, Routine, PASS 진행도)은 [[architecture]] 참고.

## 1. 제품 정체성

일반적인 헬스 기록 앱이 아니다. 핵심은:

> **"현실에서 내가 운동한 행동이 게임 진행이 되는 운동 기록 게임"**

게임처럼 캐릭터/트레이너가 존재하지만, 게임 진행의 근거는 항상 사용자의 실제 운동 기록이다. (0장에서 정의한 대로, 이 "실제 운동 기록"은 대부분 실시간 운동 세션이 끝나면서 자동으로 만들어진다 — 수동 입력은 놓친 기록을 채우는 보조 수단이다.)

- 헬스장 이용자만 대상으로 하지 않는다. 웨이트, 홈트레이닝, 러닝, 걷기, 자전거, 스포츠, 기타 사용자가 기록할 수 있는 모든 운동을 지원한다.
- NPC 대사는 "헬스장 갔냐?"처럼 특정 운동/장소만 가정하지 않는다. "오늘 뭐라도 했냐?", "몸 좀 움직였냐?", "10분 됐다", "슬슬 몸 풀렸냐?" 같은 범용/상태 기반 표현을 쓴다.
- 톤은 진지한 피트니스 서비스가 아니라 **한국식 저예산 병맛 운동 게임**에 가깝다. 가볍고 웃기되, 운동 기록 기능 자체는 제대로 작동해야 한다.

## 2. 가장 중요한 성장 원칙

**RPG식 가짜 신체 성장 시스템을 만들지 않는다.**

- "운동 10번 → 캐릭터 자동으로 헬창으로 진화" 같은 구조는 금지.
- 사용자의 몸 변화 표현은 실제 사용자가 입력한 체중/체형/사진 업데이트에 근거한다.
- 게임적 보상(레벨, 트레이너 이용권 등)은 존재할 수 있지만, 이는 외형 변화와 별개다. 게임 레벨이 몸을 바꾸지 않는다.

## 3. 최초 사용자 설정

시작 방법은 두 가지.

### A. 무료 체형 선택
- 성별 표현: 남 / 여
- 체형 프리셋 선택 (내부 ID는 중립적으로, 표시 라벨은 별도 관리 — [[architecture]] 참고)
- 체중 (필요 시 키)
- 체형 미세 조절 (프리셋을 기준으로 한 보정값)

체형 프리셋은 "멸치/평범/돼지" 3개로 끝내지 않는다. 초기 프리셋은 참고값이고, 사용자가 어느 정도 직접 조절할 수 있어야 한다. UI 표시 명칭은 추후 더 중립적인 표현으로 바꿀 수 있도록 데이터(ID)와 표시 문자열을 분리한다.

### B. 내 사진으로 시작
- 사진 선택 → 미리보기 → 계속하기 UI는 실제로 동작한다 (M2, `expo-image-picker`). 권한 거부/선택 취소/사진 없음 상태도 자연스럽게 처리한다.
- 단, 실제 AI 이미지 변환은 여전히 연결하지 않는다. 선택한 사진은 참고용 이미지로 저장될 뿐, 변환된 캐릭터를 생성하지 않는다.
- 방향: 몸의 형태가 핵심이고 얼굴 복제는 핵심이 아니다. 얼굴은 별도 고정 프리셋 선택 구조를 지원할 예정.
- 사진을 고른 뒤에도 이어서 체형 프리셋/미세 조절 화면을 거친다 — 결과가 마음에 들지 않으면 체형을 수동으로 보정할 수 있어야 한다는 원칙을 그대로 지킨다.
- 무료 체형 선택으로 시작한 사용자도 나중에 사진 기반 방식으로 업그레이드할 수 있어야 한다 (데이터 모델이 이를 지원).

## 4. 신체 히스토리

무료/유료 사용자 모두 기본 신체 기록 히스토리를 가진다 (`BodyHistoryEntry`). 구독 전용 데이터 구조로 만들지 않으며, 구독이 끝나도 과거 기록은 사라지지 않는다.

## 5. 트레이너 시스템

트레이너는 핵심 캐릭터 시스템이다. V1 대표 트레이너는 **스탠리**.

성격:
- 돈을 밝힘, 뻔뻔함
- 운동은 제대로 시킴
- 사용자를 놀리기도 하지만 과도하게 모욕/비하하지 않음
- 미워하기보다는 웃긴 캐릭터

광고와 캐릭터 성격을 연결한다. 예: "공짜로 PT 받고 싶어? 광고부터.", "내 시간은 돈이야.", "광고 하나 보고 와. 그럼 봐준다."

Trainer 데이터는 스탠리 한 명에 종속되지 않는다. 향후 실제 트레이너/유튜버 협업을 위해 `TrainerProfile` 구조로 일반화한다.

**실시간 세션 반응.** 스탠리는 운동 세션 상태에 따라 NPC 대사를 보여준다 (실제 AI 호출 아님, 결정론적 대사 풀에서 선택). 조건: 세션 시작 직후 / 오늘 두 번째 세션 / 10분 경과 / 20~30분 경과 / 장시간 운동 / 일시정지 / 운동 재개 / 운동 종료 / 첫 세트 완료 / 여러 세트 완료 / 긴 휴식 / 운동 종목 변경 / PR 달성 / 루틴 절반 진행 / 루틴 완료. 대사는 장소 중심이 아니라 상태 중심이다 — "헬스장 왔냐?" 대신 "오늘은 움직이긴 하네.", "10분 됐다.", "슬슬 몸 풀렸냐?" 같은 표현을 쓴다. 모욕적이거나 공격적인 수준은 피한다. 스탠리(게임 캐릭터)와 AI PT(6장, 실제 운동 정보/추천 도구)는 명확히 분리된 별개 기능이다.

## 6. 무료 PT vs AI PT

### 무료 기본 PT (NPC)
- **자유 채팅이 아니다.** 미리 작성된 대사 + 선택형 상호작용.
- 예: 오늘 운동 기록, 루틴 확인, 오늘 할 운동 선택, 기록 평가, 간단한 격려/놀림, 다음 행동 선택.
- 일반 게임 NPC처럼 느껴져야 한다.

### AI PT (향후 LLM 연결)
- 식단 관리, 운동 루틴 추천, 오늘 할 운동 추천, 운동 방법 설명, 기록 기반 피드백, 자유 채팅.
- 자유 채팅창만 던져주지 않는다. 빠른 선택 버튼 제공: [오늘 뭐 하지?] [루틴 짜줘] [오늘 기록 평가] [식단 봐줘] [운동법 질문] [이번 주 정리] [직접 입력].
- V1에서는 실제 AI API를 연결하지 않는다. `AITrainerService` 추상화 계층만 준비해서, 나중에 API를 붙일 때 UI를 다시 만들 필요가 없게 한다.

## 7. 광고 기반 스탠리 PT

구조: 무료 기본 NPC PT + (광고 시청 시) AI PT 기능 제한적 이용 + (유료 구독 시) 광고 없이 AI PT 무제한.

실제 AdMob SDK는 지금 연결하지 않는다. `RewardedAdService` 인터페이스 + mock 구현만 준비하고, 나중에 실제 SDK로 교체 가능하게 한다.

## 8. 구독 구조

정확한 가격은 코드에 하드코딩하지 않는다. 구독 혜택 방향:
- 광고 제거
- AI PT 접근
- 하루 1회 사진 업데이트
- 전후 비교 기능
- 추가 트레이너 혜택

사진 업데이트는 기본적으로 1일 최대 1회 구조를 지원한다. 실제 결제 SDK는 붙이지 않는다. `SubscriptionService` 인터페이스 + mock 상태로 설계한다.

## 9. 오픈 이벤트

초기 출시 시 "오픈 이벤트 무료 패스"를 지원할 예정. 기간/조건은 나중에 서버 설정 또는 config로 바꿀 수 있게 한다. 숫자를 여러 곳에 하드코딩하지 않고 중앙 config를 사용한다.

## 10. 꾸준함 보상

7~10일 정도 꾸준히 운동 기록을 달성하면 특별 트레이너 이용권을 보상하는 구조. 현재 기획상 보상은 "특별 여성 트레이너 7회 이용권"이지만, 코드에는 `rewardTrainerId`, `trainerSessionCount: 7` 같은 일반화된 형태로만 존재한다. "미녀" 등 표현이나 특정 신체 특징을 도메인 ID로 박지 않는다. 연속 기록 기준일수는 config에서 조절 가능해야 한다.

## 11. 추천인

추천인 등록 시 무료 패스 기간 +7일을 제공할 수 있는 구조. V1 로컬 앱에서 실제 추천 서버 시스템을 억지로 구현하지 않는다. `ReferralService` 인터페이스 + mock/local 상태까지만 준비하고, 향후 백엔드 연결이 가능하게 한다. 중복 추천 보상 방지를 고려한 데이터 모델을 쓴다.

## 12. 장기 트레이너 확장

장기적으로 실제 운동 유튜버/트레이너와 협업 가능. 인터뷰 → 트레이닝 철학/루틴/조언 스타일/말투 → AI 지식/프롬프트 구성 → 신규 트레이너 출시로 이어질 수 있다. 그래서 `TrainerProfile`은 스탠리 전용이 아니라 여러 트레이너를 동일 구조로 표현한다.

## 13. 기본 화면 구조 (V1)

1. 온보딩
2. 체형 설정
3. 홈
4. 운동 세션 (실시간, 탭이 아니라 홈에서 진입하는 전체화면)
5. 운동 기록 (과거 세션 확인 + 누락 기록 수동 추가)
6. 트레이너
7. 히스토리
8. 내 정보/설정

홈은 헬스 데이터 대시보드가 아니라 **게임 홈 화면**처럼 느껴져야 한다. 홈 정보 우선순위(위→아래): (1) 작은 PASS 진행도 표시(예: "HELL PASS Lv.3"), (2) 사용자 캐릭터, (3) Stanley 한마디, (4) 오늘의 예정된 루틴 또는 최근 활동 기반 제안(계획 없으면 "오늘은 뭐 조질까?"), (5) 매우 큰 **[운동 시작]** 버튼, (6) 이번 주 운동 횟수/streak. PASS는 항상 보조 요소이며, 캐릭터 + 오늘의 운동 + [운동 시작]이 홈의 주인공이다. 홈에는 전체 운동 DB, 전체 히스토리, 세트 입력 폼, 설정, 긴 AI 채팅을 두지 않는다.

[운동 시작]을 누르면 긴 입력 폼 없이 `workout-start` 화면으로 이동해 세 가지 자연스러운 진입 경로 중 하나로 즉시 `WorkoutSession`을 시작한다: **계획형**(오늘 예정된 루틴이 있으면 "오늘 · {루틴 이름}" + [이 루틴으로 시작]/[오늘은 다르게]), **즉흥형**("오늘 어디 조질까?" 부위 선택 → Exercise DB 후보), **추천형**([오늘 뭐 하지?] 결정론적 추천). 루틴이 없어도 죄책감을 유발하는 문구("오늘 계획 없음" 등)는 쓰지 않는다.

화면 계층은 명확히 구분한다: **홈 = 캐릭터 + 운동 시작 + PASS 진행도**, **운동 세션 = 실시간 세트 기록 + 타이머 + 종료**, **운동 탭 = 내 루틴/루틴 만들기/운동 DB 탐색/부위별 탐색/운동 검색/운동 정보** (더 이상 수동 기록 입력 화면이 아니다), **히스토리 탭 = 과거 결과 확인 + 전후 비교**. 과거 `WorkoutRecord`는 히스토리 탭에서 확인하며, 놓친 운동을 수동으로 채우는 입력 폼은 히스토리 탭의 하위 기능("놓친 운동 기록 수동으로 추가")으로만 존재한다.

## 14. 운동 기록 모델

`category`: `strength | home | running | walking | cycling | sports | other`. 웨이트(`strength`)가 제품의 중심축이며, 부위 선택(가슴/등/하체/어깨/팔/전신)이 주 진입 경로다. 러닝/걷기/사이클/스포츠/기타는 "[+ 유산소 추가]" 형태의 보조 경로로 제공되며 기존에 저장된 데이터는 그대로 유지된다.

`WorkoutRecord`는 대부분 실시간 `WorkoutSession`이 종료되면서 자동 생성된다(0장). 세션 진행 중에는 세트/중량/횟수 같은 상세 기록 입력을 강제하지 않는다 — "한 세트를 기록하지 않아서 운동을 완료할 수 없다"는 구조를 만들지 않는다. 상세 기록은 완전히 선택 사항이다. 웨이트 세션은 `Exercise` 단위로 세트(중량×횟수)를 기록할 수 있으며, "세트 완료 = 게임 입력"이라는 원칙에 따라 세트를 체크할 때마다 짧은 즉시 피드백(SET COMPLETE, Stanley 한마디, PR이면 NEW PR 콜아웃)을 준다. 게임 연출 때문에 실제 기록 입력이 느려지는 구조는 만들지 않는다.

## 14-A. Exercise DB / Routine / PASS 진행도

- **Exercise DB**: 정적으로 관리되는 운동 목록(`ExerciseDefinition`)이다. 서버 DB가 필요 없고, UI 컴포넌트에 하드코딩하지 않는다. 부위별로 대표성 있는 운동을 담고, 목록에 없는 운동은 [직접 운동 추가]로 보완한다.
- **Routine**: 완전히 선택 사항이다. 요일에 예약된 루틴은 그 날 홈에서 자동으로 제안되지만, 예약이 없는 루틴도 언제든 선택해 시작할 수 있다. 루틴을 만들지 않아도 [운동 시작]의 즉흥형/추천형 경로로 웨이트를 바로 시작할 수 있다.
- **이전 기록 조회**: Exercise ID 기준으로 마지막 세션의 무게/횟수/세트 구성을 조회해 현재 화면에 바로 보여준다. 같은 값을 다시 입력하도록 강제하지 않는다.
- **PR(개인 기록)**: V1은 단순하고 모호하지 않은 경우만 다룬다. 두 가지다 — **최고 중량 갱신**("이전보다 높은 중량 성공")과 **같은 중량 최고 횟수 갱신**("같은 무게로 전보다 더 많이"). 뒤엣것은 중량이 늘지 않는 맨몸 운동(풀업/푸쉬업)의 유일한 성장 표시라서 넣는다 — 중량 기준만 두면 그 종목들은 영원히 PR이 없다. 처음 해보는 중량에서는 횟수 PR이 나지 않는다(비교 대상이 없고, 새 무게마다 PR이 터지면 PR이 값을 잃는다). 한 세션의 한 운동에서 두 종류가 동시에 나면 중량 쪽만 남긴다. **복잡한 1RM 계산은 여전히 하지 않는다** — 판정에 쓰는 것은 사용자가 실제로 든 무게와 횟수뿐이다.
- **PASS 진행도**: 세션 완료/루틴 완료/PR/주간 목표 같은 실제 운동 행동이 PASS XP를 올릴 수 있다. **PASS XP는 게임 진행도다. 사용자의 실제 몸/근육 수치를 직접 올리지 않는다** — 2장의 성장 원칙과 동일한 경계를 PASS에도 그대로 적용한다.

## 14-B. 운동 세션 조작 원칙 / 성장 계산 경계

운동 중에는 게임보다 실제 운동 편의성이 우선이다. 세션 화면에서 사용자가 하는 일은 **중량 확인/수정 → 횟수 확인/수정 → 세트 완료** 세 가지뿐이어야 한다. "지금 채울 세트"는 앱이 항상 준비해 두고(지난 기록을 기본값으로 제안), 세트를 완료하면 확인창 없이 곧바로 휴식이 시작되고 다음 세트가 준비된다. 운동 중 팝업/퀴즈/불필요한 화면 이동을 만들지 않고, 중량·횟수 버튼을 작게 만들지 않는다.

**Motion Family**: 종목마다 캐릭터 애니메이션을 만들지 않는다. 공통 모션 패턴(수평 밀기/수직 당기기/스쿼트/힙 힌지/코어 …) 하나에 여러 종목이 붙고, Exercise는 `animationFamily`로 그중 하나를 가리킨다. 캐릭터는 운동 경험을 방해하지 않는 범위에서 존재한다.

**성장 계산 경계**: 세션이 끝나면 `WorkoutSessionResult`(총 시간/세트/반복/볼륨/운동별 기록/PR/부위별 볼륨)가 만들어지고, 이것이 GrowthEngine의 유일한 입력이다. GrowthEngine이 돌려주는 것은 게임 진행도(부위별 SP)이며 **실제 체중/체지방률/골격근량이나 캐릭터 외형 파라미터를 만들거나 바꾸지 않는다** — 2장의 성장 원칙과 같은 경계다.

**Muscle SP**: 실제 운동 기록이 부위별 성장 포인트로 쌓인다. 판정 기준은 절대 중량이 아니라 **사용자 기준 상대 강도**다 — 같은 60kg라도 누군가에겐 최대치, 누군가에겐 워밍업이므로 같은 노력에 같은 성장을 준다. 맨몸 운동도 체중을 부하로 계산해 0점이 되지 않는다. 반대로 가벼운 무게 무한 반복, 비정상적인 중량 입력, 같은 부위 과도한 세트로는 SP가 폭증하지 않는다 — 게임 보상 때문에 위험하거나 무의미한 운동을 하게 만들지 않는다.

**성장 속도**: 부위별 stage는 0~5이며 threshold는 비선형이다. 첫 주에 0→1이 보이도록 빠르고, 뒤로 갈수록 느려지며, 최종 단계는 장기 목표다. 한 번의 운동으로 여러 단계가 점프하지 않는다 — 운동 한 번에 다른 몸이 되는 연출은 실제 운동과 맞지 않는다. **Account Level(PASS XP)과 Muscle SP는 별개의 축이며 서로의 alias가 아니다.**

## 14-C. 단백이 몸 상태 (근육 × 지방)

단백이의 몸은 **독립된 축들의 조합**이다: 근육(운동 기록에서만), 지방/데피니션(실제 체지방률·체중 추세·식단), 일시적 펌핑, 회복. 근육이 늘었다고 체지방이 저절로 내려가지 않고, 식단을 잘했다고 근육이 생기지 않는다. 같은 근육 단계라도 지방 상태가 다르면 다른 몸이 나온다 — 운동 많음+관리 좋음은 선명한 헬창, 운동 많음+관리 나쁨은 큰 체형, 운동 적음+관리 좋음은 마른 몸, 운동 적음+관리 나쁨은 말랑한 몸. 이 네 가지는 고정된 클래스가 아니라 입력의 결과이며, 사용자는 언제든 다른 방향으로 옮겨간다.

**체지방 표시 원칙**: 실제 체지방률은 사용자가 직접 입력한 값(또는 향후 신뢰 가능한 측정 소스)에서만 온다. 데이터가 없을 때 앱이 만드는 것은 캐릭터 표현용 내부 단계일 뿐이며, 그것을 실제 체지방률처럼 보여주지 않는다. 의학적 판정 문구도 쓰지 않는다.

**성장 표현 곡선**: 초반 변화는 미세하고 후반으로 갈수록 커진다. 마지막 단계는 평범한 운동 체형이 아니라 과장된 단백이다. 반대로 한두 번 운동했다고 즉시 거대해지지 않는다.

## 15. V1에서 실제로 연결하지 않는 것

- 실제 AI 이미지 생성 API
- 실제 LLM API
- 실제 광고 SDK
- 실제 인앱결제
- 실제 추천인 서버
- 실제 계정 서버
- 실제 유튜버 트레이너
- 복잡한 백엔드
- 소셜 기능 / 랭킹
- 과도한 RPG 성장 시스템

대신 나중에 연결하기 쉬운 인터페이스만 준비한다 ([[architecture]] 의 서비스 경계 참고).

## 16. 기술/UX 원칙

- 현재 Expo / React Native / TypeScript 구성을 유지한다.
- 모바일 우선, Android 우선 개발하되 불필요하게 iOS 호환성을 깨지 않는다.
- 세로 화면 기본, 터치 영역은 충분히 크게.
- 비즈니스 로직을 화면 컴포넌트에 몰아넣지 않는다 (도메인/서비스/UI 분리). 단, 초기 V1에 불필요한 엔터프라이즈급 추상화는 하지 않는다.

## 17. 데이터와 설정

변경 가능성이 높은 값은 중앙 config(`src/config/app-config.ts`)로 관리한다: `streakRewardDays`, `rewardTrainerSessions`, `referralBonusDays`, `dailyPhotoLimit`, `rewardedPtUses`, `openEventPassDays` 등. UI 문자열과 내부 ID를 가능한 한 분리한다.

## 18. 저장

V1은 로컬 저장(AsyncStorage)으로 시작한다. 최소 저장 데이터: 사용자 프로필, 신체 설정, 신체 히스토리, 운동 기록, 연속 기록, 트레이너 이용 상태, mock 구독 상태, 이벤트 패스 상태, 추천 보상 상태.

## 19. 아트

최종 아트 에셋 제작 단계가 아니다. placeholder(이모지/도형)를 사용한다. UI 구조가 이미지 파일 경로에 강하게 종속되지 않게 한다. 향후: 실사/사진 기반 사용자 몸 표현, 얼굴 프리셋 선택, 강한 캐릭터성의 트레이너, 스탠리는 기존 확정 디자인 유지.

## 20. 안전한 운동/AI 설계

향후 AI PT가 추가되어도 의료 진단 기능으로 만들지 않는다. 통증/부상/질환 등 의료적 판단이 필요한 상황에서 AI가 확정적 진단을 내리지 않도록 하는 안전 규칙을 구조적으로 고려한다. 극단적인 식단/위험한 운동을 강요하는 캐릭터 설계를 피한다.
